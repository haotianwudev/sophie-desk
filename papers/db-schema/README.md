# papers.db schema

Reference for the local SQLite index built from this vault's own markdown (`papers/`,
`papers/candidates/`, `tasks/`) plus any Source DB (`gdocs/db/gdocs.db`) — see
[DATABASES.md](DATABASES.md) for the full registry, the Index-DB-vs-Source-DB distinction,
and how to add a new table to either kind. The database itself lives at
[papers/paper-index/papers.db](../paper-index/) (gitignored, **fully disposable** — deleted
and rebuilt from scratch every run, never edited in place) — these notes document its
*shape*, they aren't the database. **Want current row counts, freshness, and what needs
attention right now instead of a schema reference? See [STATUS.md](STATUS.md).**

**This is what `Papers.md` renders off, as of 2026-09-05** (needs the **SQLite Explorer**
Obsidian plugin, via `sqlite-query` blocks). `Desk.md` was tried on this DB too and reverted
back to Dataview the same day — tasks change too often for a rebuild-based board to feel live,
so it kept Dataview's true liveness; Dataview is still required for that one board.
The tradeoff for `Papers.md`: not *live*. Nothing rebuilds this on a timer (that was tried via
the supervisor and reverted, see `DATABASES.md`) — a rebuild happens when whatever changed the
underlying data triggers one (a Source DB script's own last step, e.g.), or when you run it by
hand.

**Source of truth stays the markdown (or, for `gdocs`, its own Source DB).** Nothing here is
hand-maintained data in `papers.db` itself; it's a map of what querying the DB gets you. The
actual build script and full column-level schema live in the `sophie-pipeline` repo, not this
vault:

- `sophie-pipeline/paper-index/build_index.py` — the builder
- `sophie-pipeline/paper-index/schema.sql` — the authoritative `CREATE TABLE` statements
- `sophie-pipeline/paper-index/README.md` — rebuild command, querying examples, Obsidian
  SQLite-plugin setup

Rebuild any time `papers/`, `papers/candidates/`, or `gdocs/db/gdocs.db` changes:

```bash
cd /f/workspace/sophie-pipeline/paper-index
python build_index.py
```

## Tables

| Table | Rows from | Note |
|---|---|---|
| [papers](papers.md) | `papers/<category>/*.md` frontmatter | one row per paper note |
| [candidates](candidates.md) | `papers/candidates/*.md` tables | one row per backlog candidate |
| [gdocs_index](gdocs_index.md) | `gdocs/db/gdocs.db` (Source DB) | raw Google Drive `.gdoc` stub scan |
| [article_gdoc_matches](article_gdoc_matches.md) | `gdocs/db/gdocs.db` (Source DB) | article slug → matched Drive doc |
| [tasks](tasks.md) | `tasks/*.md`, `tasks/done/*.md` | one row per task — feeds `STATUS.md`, not `Desk.md` (that stays on Dataview) |
| [pipeline](pipeline.md) | `notes/pipeline/*.md` | pipeline health; empty until that folder exists |

`gdocs_index` and `article_gdoc_matches` are only populated when `gdocs/db/gdocs.db` exists on
the machine running the build — that directory is gitignored personal data (the user's own
Drive research-session titles), present only on their workstation, never in this public repo.

`Skills.md` doesn't use this DB — it's entirely regenerated by `scripts/gen_skills.py`, which
computes its two filtered tables directly from the same in-memory data it already has (no
query needed, live or otherwise).

## A parsing gotcha worth knowing before trusting a query

`candidates` (and, until 2026-09-06, `gdocs_index`/`article_gdoc_matches` before those moved
to a real Source DB) is parsed out of markdown pipe-tables. A literal `|` inside a cell is
written `\|` per standard markdown escaping, and the shared row-splitter respects that
(splits on *unescaped* `|` only, then un-escapes `\|` back to `|`) — but this was a real bug
until 2026-09-05: naive `str.split("|")` silently shifted every later column by one for any
row whose title/why text contained an escaped pipe. It corrupted `status` in 3 `candidates`
rows and `match_tier`/`matched_doc_id` in 1 `article_gdoc_matches` row (back when that came
from markdown) before the fix. If a future markdown edit reintroduces raw (unescaped) pipes in
a cell instead of `\|`, that same corruption pattern will return for `candidates` — worth a
spot-check (`SELECT DISTINCT status FROM candidates` should only ever show real status
strings, never a title/link fragment) after any bulk edit to a candidates source file.
